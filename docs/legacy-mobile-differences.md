# 旧PC版と旧Android版の生成差異

調査日：2026-10-27。すべてテスト専用資料と架空入力で検証。実データは使用していない。

## 結論と現在の方針

提供67件の最新salt出力は、旧PC版の固定期待値、新PC互換コア、旧Android版で一致した。ただし、追加検証で **二進数の剰余計算と乱数の境界処理に独立した差異** が見つかった。67件一致は、すべての入力での互換性を示さない。

デスクトップは設計どおりPC互換の`legacy-pc-v1`として実装した。調査と追加説明を確認後、ユーザーから剰余・乱数の両方について移行の容易さを優先する承認を得た。新Androidも実装・検証済みのPC互換コアを共有し、旧Android固有の丸め・乱数境界処理は再現しない（[ADR 0006](decisions/0006-shared-pc-generator.md)）。旧ソース・差異の固定資料は保持し、Androidアプリへの機能接続・実機確認は未実施。

追加確認（2026-10-27）：ユーザーより、既存の本番データには生成長10文字未満のレコードがないと申告を受けた。実データの読込・確認はしていない。差異1の剰余計算は移行の容易さを優先し、すでに共通コアで実装・検証済みのPC版の正確な整数計算を採用する。旧Androidの丸めを再現する別実装は追加しない。当初は差異1のみの決定だったが、その後、差異2も同じ判断を行う承認を得た。乱数はPCのJava/Scala互換を採用する。

## 参照元・検証方法

- PC：`passwordManager`コミット`9840d111cab0f0634cfaa1a50dd6c81da28cafc1`の`PasswordGenerator.scala`、`Record.scala`、`LineSeparators.scala`。Scala 2.12.13の既存キャッシュを使い、コピーした未変更ソースを隔離一時ディレクトリでコンパイルして92件の合成期待値を採取した。GUIは起動していない。
- Android：`password_manager_sp`コミット`015b9c10f62183965aa7bb10881c42c22c33e612`の`util.js`、`random.js`、`binary.js`。コピーをテスト内のNode VMで実行。import/exportの除去とSHA-512のNode実装への注入のみ行い、生成・乱数・二進演算の本体は変更していない。ファイルI/O・React Native・実機は実行していない。
- 原本とコピーのバイト一致をGitオブジェクトで確認し、`packages/compatibility-fixtures/sources.json`に出典とSHA-256を記録した。
- 自動再検証：`source scripts/env.sh`の後に`npm test`。外部リポジトリ、Java、Scala、追加ライブラリ、ネットワークは不要。
- 新実装から旧期待値を生成していない。67件はユーザー提供GUI期待値、92件は今回の旧PCソースからの採取値として区別する。過去saltの67件に対応するGUI期待値は引き続き未採取。

## 1. 大きな整数をNumberへ変換する際の丸め

旧Androidの`Binary.mod()`は、長い二進数から除数のシフト値を一度引き、その残りを`parseInt(..., 2)`でJavaScriptの`Number`に変換してから`%`を実行する。PCの`BigInteger`/`BigInt`は整数精度を失わない。

パスワードの1文字に使うビット数は`floor(512 / 長さ) - 1`。長さ8では63bit、9では55bitとなり、変換時に整数精度の上限を超え得る。長さ10以上では最大50bitなので、この剰余計算による丸め原因は生じない。ただし、後述の乱数の差があるため、長さ10以上の出力一致を一般には保証できない。

### 旧PCのマスター入力制限を満たす具体例

共通入力は次のとおり。以下の文字列はすべて架空のテスト入力・出力。

```text
master: dummyMaster1
salt: 0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz01
大文字: false
数字: false
記号: 空文字列
```

| 長さ | 旧PC / 新PC互換コア | 旧Android          | 結果           |
| ---- | ------------------- | ------------------ | -------------- |
| 4    | `wqez`              | `jbfr`             | 不一致         |
| 8    | `abaxksql`          | `ppjwwtdc`         | 不一致         |
| 9    | `jwjgqxitm`         | `jwjgqxitd`        | 末尾のみ不一致 |
| 10   | `togqqnzzbm`        | `togqqnzzbm`       | この入力は一致 |
| 16   | `zdixianqxkcgzvbs`  | `zdixianqxkcgzvbs` | この入力は一致 |

同じマスター・saltで大文字と数字を必須、記号を`!@#`、長さ4にすると、PCは`#Id3`、Androidは`#oP9`だった。生成結果が異なっていても、両方とも文字種条件を満たす場合がある。

長さ8の例の最初の分割値では、一度減算した後の正確な整数は`4068439027050693324`。`Number`が保持する整数は`4068439027050693120`となり、204だけずれる（通常の文字列表示では`4068439027050693000`）。この分割値に対応する文字インデックスはPCの16に対してAndroidの20だった。ハッシュそのものは両実装で一致し、剰余計算の入力まで遡って原因を切り分けた。

異なる架空入力（`synthetic.json`のindex 76）では、長さ4、必須4文字種でPCが`?o3G`を返す一方、Androidは101候補を使い切って空文字列を返した。文字の違いだけでなく、生成できるかどうかにも影響し得る。

### 影響条件

- 長さ1〜9で分割値が精度を超える場合が対象。旧PCの登録UIは4以上だったため、通常の既存登録では特に4〜9を確認する必要がある。
- 入力・salt・文字集合によって、丸めが起きない、剰余が偶然一致する、再試行後に一致する場合がある。「9以下は必ず違う」とは判断できない。
- 新規登録で承認された8〜64文字のうち、8・9もこの問題の範囲に入る。新PC版はPC互換であり、旧Androidへの逆書き出しは行わない。
- 二進演算をBigIntへ置き換えるとPCの数学的計算に近づくが、旧Androidの既存出力を変え得る。

## 2. 乱数nextInt(bound)の整数オーバーフロー

旧Androidの`Random.nextInt(bound)`は、Java/Scalaと同じ棄却条件を記述しているが、`bits - value + (bound - 1)`をJavaScriptの通常のNumberで評価する。Javaは符号付き32bitのオーバーフローを起こし、その候補を棄却する。Androidは正のNumberのままなので棄却しない。

```text
seed = 76974151
bound = 26
最初の31bit値 = 2147483625
最初の剰余 = 1
棄却判定の式 = 2147483650
Javaの符号付き32bit解釈 = -2147483646
```

| 実装                       | nextInt(26)                       |
| -------------------------- | --------------------------------- |
| Java 17 `java.util.Random` | 7（最初の候補を棄却して次を採用） |
| 新PC互換コア               | 7                                 |
| 旧Android                  | 1（最初の候補を採用）             |

Java単体の小さなプログラムと旧Androidの未変更ソースで独立して再現し、回帰テストを追加した。このseedは生成本体のseed合計の範囲内で、上限26は小文字のみのshuffleの最初の段階で実際に使われる。

### 小文字のみの場合に限るのか

**小文字のみでも起こり得るが、小文字のみには限定されない。** 上記は説明と再現を簡単にするため、候補文字26個の最初の乱数呼出を切り出した例。

shuffleは「残り候補の何番目を選ぶか」を乱数で決め、残り個数を1つずつ減らす。小文字のみなら上限は26→25→…→2、大文字も含めると52→51→…→2、さらに数字を含めると62→61→…→2となる。したがって、大文字・数字・記号を含む場合も、上限26などの問題が起こり得る段階を通る。2の累乗の上限には別の分岐があるが、shuffle全体にはそれ以外の上限も含まれる。

直接の発生条件は、該当する乱数呼出で`bits - (bits % bound) + (bound - 1)`が`2147483648`以上になること。上限26なら、31bit乱数値が`2147483624`〜`2147483647`の範囲に入ると該当する。PCはこの値を捨てて次の乱数を使い、旧Androidはそのまま使うため、以降の並べ替え結果が変わり得る。

ただし、大きな文字集合では上限26へ到達する前にも乱数を消費するため、上記と同じseedを与えたらすべての文字種設定で同じ箇所に差が出る、という意味ではない。条件を決めるのはマスターとsaltから導くseed、候補文字数、再試行回数、およびそれまでの乱数消費。同じマスター・salt・生成条件を使う限り結果は決定的であり、実行のたびに偶発的に変わる現象ではない。

この差異はパスワード長に依存しない。乱数が棄却境界を踏むと文字集合のshuffleが変わり、10文字以上でも出力差異の原因になり得る。ただし、**特定のマスターとsaltからこのseedが導かれる入力探索は行っていない**。今回の証拠は乱数単体の確定した差異であり、10文字以上の具体的なマスター・saltによる生成不一致例とは区別する。

## 別の解析差異と検証の限界

旧PCの真偽値解析は`TRUE`をtrueとして扱うが、旧Androidは文字列`true`との完全一致で判定する。新パーサーはPCに合わせる。通常の旧PC保存出力は小文字のため、手編集・他の書出元などで影響が出得る。

旧PCの`getBytes`は文字コード指定がない。今回の合成期待値は既定文字コードUTF-8で採取した。新mainのハッシュもUTF-8を明示する。有効なUnicode文字列は合成ケースで検証したが、別の既定文字コードで動いていた旧PC、不正なサロゲート、全入力の一致を保証するものではない。通常の旧PC UIのマスターと生成saltは英数字。

旧Androidの生成不能時の空文字列、末尾改行による旧読込失敗なども新PCへ持ち込まない。これらは旧互換の差異として記録し、実データを黙って補正しない。新Androidの既知の剰余・乱数差異はPC互換へ統一するが、ここに記した別の入力・解析差異まで一括で変更する承認とは扱わない。
